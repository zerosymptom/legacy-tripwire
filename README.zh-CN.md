# Legacy Tripwire

**AI 在遗留系统里施工时反复踩的 40 个「零症状」坑，以及每个坑的机械判据。**

语言：[English](README.md) · 简体中文

---

## 这是什么

主体是一份清单：[**RULES.zh-CN.md**](RULES.zh-CN.md) —— 40 条规则，
每条包含「症状 / 机械判据 / 为什么 AI 查不出 / 误报边界 / 核实时间」。

其中 **3 条已经是可执行的检查**（[`engine/`](engine/)，Java 17、零运行时依赖）。
其余仍是文档 —— 一部分是还没写，一部分是**本来就不该机械化**（见「怎么用」）。

全部来自一套真实的 Java 遗留系统（Spring MVC + Dubbo + MyBatis + MySQL 5.6/8.0，
部分模块 `source` 还停在 1.7）上一年多的 AI 辅助施工记录，**每条都至少让人或 AI 浪费过一次排查**。

## 为什么是「零症状」

这 40 条有一个共同形态，它决定了为什么 AI 查不出来：

> **成功信号是真的，事情没发生也是真的。**

- `BUILD SUCCESS` 是真的 —— 只是执行了 0 个用例（[LT-S01](RULES.zh-CN.md#lt-s01-构建配置里的字面量跳过测试压过命令行参数)）
- `OK (0 tests)` 前面那几十行干净的类名列表是真的 —— 只是一条都没跑（[LT-S05](RULES.zh-CN.md#lt-s05-shell-不做单词分割批量运行静默变成单参数)）
- 「核验命令无输出 = 通过」是真的 —— 只是 diff 范围里根本没有你的改动（[LT-S06](RULES.zh-CN.md#lt-s06-ahead-的-diff-不含未提交改动让所有期望无输出的核验假绿)）
- 测试写了、跑了、全绿、提交了 —— 只是 `.gitignore` 忽略了整个测试目录（[LT-S04](RULES.zh-CN.md#lt-s04-版本控制忽略整个测试目录)）
- 构建成功、镜像推送成功、容器 `Up`、本地全量测试全绿 —— 只是配置文件里有一个 emoji，
  整个应用起不来、全路径 500、**一行日志都没有**（[LT-P01](RULES.zh-CN.md#lt-p01-容器的-xml-解析器只支持-3-字节-utf-8一个-emoji-让整个应用起不来)）

AI 能观察到的，恰恰就是那个「真的」。
**它不是不够聪明，是这些场景下的反馈信号本身就是错的。**

## 九个类别

| 类别 | 含义 | 条数 |
|---|---|---|
| `SILENT` | 跑了、没报错、什么也没发生 | 15 |
| `CONTRACT` | API / 命令的隐含语义与直觉相反 | 6 |
| `PLATFORM` | 运行时或中间件的硬限制，触碰即整体失效 | 11 |
| `ENV_MIS` | 本机 / 容器 / 工具链状态让结论失真 | 3 |
| `FALSE_ALARM` | 工具报了一个不存在的问题，或谎称做过某事 | 4 |
| `TOPOLOGY` | 实际有 N 条链路，只看见 1 条 | 1 |
| `SEM_INV` | 方法名 / 配置名与实际语义相反 | 私有语料 |
| `NO_SUBSYS` | 以为存在的子系统在这条产品线根本不存在 | 私有语料 |
| `DEAD_SRC` | 读的是一处再也不更新的数据源 | 私有语料 |

后三类的全部样本都与具体业务强绑定，无法脱敏发布，只保留类别定义。

## 怎么用

**现在**：当检查清单用。AI 给你交付之前，对着它过一遍 ——
尤其是任何形如「跑通了 / 全绿了 / 无输出即通过」的结论。

**判据分两种，别混用**：

- `MECHANICAL` —— 一条命令就能判定，可以进 CI / 提交门禁。
- `MANUAL` —— 只能人判。⛔ **不要**放进自动拦截。
  误报会让 AI 去改**本来是对的**代码，代价高于漏检。

**每条都有 `verified` 日期，因为规则会过期。** 引用前请自行复核一次 ——
语料里已经有一条规则在被写下之后就被上游修掉了。

## 这些数字是怎么来的

| | |
|---|---|
| 原始语料 | 1,829 条 AI 协作记忆（个人 58 条 + 多个 agent 的 1,771 条） |
| 抽样 | 100 条（58 条全量 + 42 条抽样） |
| 标注方式 | 人与模型**各自独立**标注，事后逐条对账 |
| 四个轴 | ① 是否雷区 ② 哪一类 ③ 能否机械断言 ④ 可移植性 |
| 可机械断言比例 | **20.7% ~ 60.3%**（两套独立口径的下界与上界） |
| 预设的止损线 | 低于 15% 就砍掉整个项目 |

方法、分歧和一处**我自己的归因被实测推翻**的过程，写在
[**这篇文章**](docs/article.zh-CN.md)里。

⚠️ 两套口径差了近三倍，而**瓶颈不在「能不能机械判定」，在「什么算一个坑」** ——
收窄到两边都认是坑的条目后，机械断言率只差 7 个百分点。这个发现比那个比例本身更有用。

## 后来拿公开基线量了一次

第二次实验换了语料：不是事后写的笔记，是**原始会话记录**——
30 个会话、185 条开发者发言，照同样的「先盲标、后套分类」做了一遍，
再去对标一份公开研究（两万多个会话、一千六百多个仓库，七类症状 + 一个每轮失准率基线）。

| | |
|---|---|
| 当场失准率（公开口径） | **0.057**　vs 公开基线 **0.051** —— 基本持平 |
| 事后返工率（公开口径测不到的） | **0.205** |
| **当场不暴露的失败占比** | **≈ 2/3** |
| 事后暴露那批里，公开七类**装不下**的 | **42%** |
| 标注一致率 / Cohen's κ | 81.3% / **0.296** |

**两个可以直接拿走的结论：**

1. 🔴 **「标注一致性 0.83」这类说法要看它量的是哪个指标。** 本次逐条一致率 81.3%，
   几乎等于那份公开研究报的 0.83；但 κ 只有 0.296 ——
   在正负样本极度不平衡的任务上，一致率是个很宽容的指标，而那份研究没报 κ。
2. 🔴 **公开分类法有一个空格子**：它有「谎报自己的工作状态」，
   但没有任何一类对应「**在产出的内容里编一个事实**」。
   本仓文章开头那个故事，最初写的时长就是编出来的数字，后来才被改正 ——
   说做完了而没做完，和编一个从没发生过的数字，是两件事。

装不下的那 42% 有个共同点：**信息压根不在 AI 能看到的地方**（页面渲染结果 / 团队内的约定与归属 /
另一个仓库里的对端实现 / 一份写的时候正确、两个月后失效的方案）。
这正是本仓想覆盖的那条边界。

⚠️ 限制见[文章第九节](docs/article.zh-CN.md)，其中两条必须一起读：
**另一个标注者就是被评判的那个 AI**（所以「谎报工作状态」那一类标出来是 0，判为方法缺陷而非成绩）；
**抽样脚本不可复现**（会话池在变，重跑拿到的不是同一批数据，且无任何报错）。

## 能跑的那部分

40 条里有 3 条已经是**可执行的检查**，在 [`engine/`](engine/)：

```bash
cd engine && mvn -q package
java -jar target/tripwire.jar /你的/代码库
```

| | 查什么 |
|---|---|
| **LT-S01** | 构建配置里的字面量「跳过测试」压过命令行 —— `mvn test` 报成功、跑了 0 个用例 |
| **LT-S04** | 版本控制忽略了测试目录 —— 本地能编译能跑能过，提交后就没了 |
| **LT-P01** | 部署描述符里有 U+FFFF 以上的字符 —— 容器解析失败，全路径 500 且一行日志都没有 |

两条刻意的设计：

- **退出码 `2` 表示「判不出来」，而且是非零的。** 这里查的每一样东西都长得和成功一模一样；
  一个在拿不到结论时退出 0 的检查器，本身就是同一个 bug。⛔ 没有任何一个退出码表示「没查出来，接着走」。
- **每次运行都打印「看了多少个文件」**，包括干净的那次。
  「没有发现」在看了 40 个文件和看了 0 个文件时读起来一模一样，而后者才是会悄悄停止保护你的那种。

⛔ 只有 `MECHANICAL` 判据进引擎。需要人判断的那些留在文档里 ——
误报会让 agent 去改本来是对的代码，代价高于漏检。
新增规则必须同时带一个会命中的用例和一个不该命中的用例，否则构建失败。

## 范围与边界

- ✅ 公开的是**模式**，不是现场。所有规则已去掉模块名、库名、配置键名与业务语义。
- ⛔ 不收「某框架某版本的 bug」这种查一次文档就能解决的事。收的是**反馈信号本身撒谎**的场景。
- ⛔ 不保证完整。它的来源是一个人的一套系统，**样本有偏**，这一点没法靠努力消除。
